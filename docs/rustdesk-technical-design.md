# RustDesk macOS 伴侣应用技术设计

状态为待实现。适用基线为 `decouple-rustdesk` 分支的 `df365a4`。首个交付场景是用户在手机上通过自建 RustDesk 操作 Mac 上的一份文档，断开后回到原来的桌面。[产品需求与验收用例](PRODUCT.md)定义交付条件，[交接说明](../AGENT_HANDOFF.md)记录选型背景。

## 1. 进程边界与代码落点

RustDesk 继续处理连接、认证、加密、画面传输与客户端选屏。伴侣应用在被控 Mac 上读取本地会话信号，让 macOS 创建虚拟屏、移动窗口及处理输入。M0 沿用 RustDesk 已有的服务器配置。型号和方向由用户在 Mac 上选择，远端正在观看的屏幕在没有可靠信号时显示为未知。

| 边界 | 基线入口 | 拟改动 |
|---|---|---|
| 本地观测 | [AppController](../Sources/Snug/App/AppController.swift) 每 0.5 秒向 UUSensor 取样，再交给 RemoteSession | 将 RustDesk 观测放在应用层 Sensing 目录。耗时读取移出主线程，主线程串行接收最新有效样本。继续由 AppController 统一更新菜单状态和屏幕计划。 |
| 会话解释 | [RemoteSession](../Sources/SnugCore/Session/RemoteSession.swift) 及同目录的 UU 信号、日志解析 | 核心层只接收活动、空闲或未知，以及可用时的会话标识。按下节规则产生开始、中断、恢复、结束；移除 UU 控制端表与采集日志依赖。 |
| 显示与窗口 | [ScreenPlan](../Sources/SnugCore/Screens/ScreenPlan.swift) 计算期望屏幕，[DeskSet](../Sources/SnugCore/Screens/DeskSet.swift) 执行，系统层负责建屏与 AX 操作 | 保留按配置计算屏幕、串行协调系统操作的分工。调整常驻主屏和权限策略，复用已有的机型库、HiDPI 档位和恢复记录。 |
| 输入 | [TouchTap](../Sources/SnugSystem/TouchTap.swift) 使用 [TouchEvents 中的 UUEventSource](../Sources/SnugSystem/TouchEvents.swift) 按注入进程筛选事件 | 替换来源匹配，保留事件监听和 [TouchTranslator](../Sources/SnugCore/Touch/TouchTranslator.swift)。只对已证实可识别的输入启用翻译。 |
| 分发、配置与诊断 | [SnugPaths](../Sources/SnugCore/Persistence/SnugPaths.swift)、[UpdateSource](../Sources/SnugCore/Update/UpdateSource.swift)、[构建与发布脚本](../scripts/snug) | 隔离配置、日志、签名和更新通道，替换旧感知命令。沿用 Swift 包分层，首版无需新增服务或单独的 SDK。 |

## 2. 如何判定一次远控

先在目标版本上观察空闲服务、手机连入、切屏、断开、重连五个时间点，核对本地可访问的活动会话状态、IPC 或日志。记录信号何时出现、消失、读取失败，以及应用在连接中途启动时能否取得当前状态。选取能区分真实活动与空闲的最小信号源；日志候选还要验证轮转、旧行重读和进程重启。具体接口、路径、事件名和等待时长均待实测。

| 观测与当前状态 | 核心层决策与副作用 |
|---|---|
| 空闲时首次确认有活动会话 | 建立一次会话，应用屏幕计划。重复的活动样本只更新状态，保留已有窗口快照。 |
| 活动中明确失去连接 | 暂停输入翻译，进入待重连。期限内恢复时沿用屏幕和窗口；期限届满且确认无活动会话，执行一次结束与还原。用户也可明确结束。 |
| 读取失败、权限丢失、观测源重启 | 转为未知，暂停输入翻译并说明原因。保留已接管的窗口和恢复记录；重新取到完整状态再决定恢复或结束。菜单提供手动结束，避免无限等待。 |
| 手动开始或结束 | 通过同一会话入口执行，标记手动模式；旧的自动样本不得重开已结束的会话。切回自动时重新读取当前状态。 |
| 有第二个控制端或过期样本 | 若能枚举会话，最后一个退出才触发还原。若信号不能判定是否还有控制端，显示未知并允许手动结束。丢弃旧观测周期返回的结果。 |

连接感知只回答“是否正被远控”。客户端切屏、Mac 显示器重排、鼠标进入虚拟屏，都不能单独证明连接开始或结束。若候选信号均不可靠，交付手动模式并将 M0 自动感知记为未通过。

## 3. 从建屏到还原

1. **准备屏幕。** M0 仅启用一块手机竖屏，使用用户选择的型号与方向生成 ScreenWish。自动确认连接或手动开始后建屏，用户在 RustDesk 端切入。默认保留原主屏。当前 ScreenPlan 会在空闲时保留指定主屏，迁移时要将“本次会话临时设主屏”的生命周期与旧规则分开。
2. **改变主屏与排布。** 用户选择临时主屏时，先记录已有屏幕身份和原点，再调用 [DisplayArrangementService](../Sources/SnugSystem/DisplayArrangement.swift)。失败时保留普通选屏路径并显示失败状态。重排或热插拔后重新枚举，只有确认由本应用创建的显示器才能纳入撤屏范围。
3. **接管窗口。** 复用每屏的 `placed/` 记录，保存原窗口身份、位置和大小，再搬移、铺满。字号记录本次实际施加的级数，`zoom.json` 保存用户偏好。写入恢复记录失败时停止这次搬移，保留原窗口。
4. **结束会话。** 停止手势和新增搬移，恢复原排布，在正确的坐标系中恢复窗口及字号，再释放本次虚拟屏。幂等处理重复结束事件。原显示器拔除或窗口已关闭时，保留可恢复项并说明原因；窗口返回时使用 [LeftBehindLedger](../Sources/SnugCore/Screens/LeftBehindLedger.swift) 的识别和字号作用域规则。
5. **异常后启动。** 取得辅助功能权限后先调用已有的 DeskSet.recover，再接收新会话的搬移请求。当前 [ScreenSet](../Sources/SnugCore/Screens/ScreenSet.swift) 仅在内存保存原排布，窗口账本无法替代排布快照。M1 还需验证强杀发生在设主屏后、字号调整中和部分窗口已恢复后三个位置；为临时排布补齐跨重启记录，只恢复身份能核实且仍在线的屏。对无法判断是否已发送的字号快捷键，保留待处理提示，避免重放造成二次缩放。

P0 并装隔离也涉及虚拟屏身份。[ScreenWish](../Sources/SnugCore/Screens/ScreenWish.swift) 以 vendorID、productID 和序列号组合标识屏幕。为派生版分配与原版不同的组合，同步核对[探测屏](../Sources/SnugSystem/ProbeDisplay.swift)，实测两版同时建屏、单独撤屏后各自排布仍正确。

M1 扩展手机横屏、平板和电脑屏时继续用相同的屏幕计划与恢复流程。验证已有物理屏、其他软件的虚拟屏及原版 Snug 共存，按枚举结果判断可用性。工具栏避让尺寸从实际客户端画面测量，分别检查横竖屏可见区域。具体支持的屏数和设备组合随实测结果发布。

## 4. 手势与权限

输入翻译需要同时满足四个条件：会话有效、来源可确认、坐标位于本应用的触屏区域、当前模式已验证。保留现有合成事件标记，避免应用消费自己产生的滚轮或右键事件。重排时刷新区域，断开或权限丢失时清除长按计时和惯性，普通屏、本机鼠标和未知来源的事件原样交给系统。

M0 用同一文档分别测试本机鼠标、手机触摸模式、手机虚拟鼠标模式。比较按下、移动、抬起、原生滚轮和右键事件的顺序、坐标与来源；再单独测试本机鼠标位于虚拟屏的情况。确认能区分后才启用单指惯性滚动、长按右键及长按拖选。若来源不可区分或客户端已将输入翻译成滚轮，保留原生输入并在 UI 标出相应模式的限制。

辅助功能权限影响移窗与输入。基线 ScreenPlan 缺此权限会直接返回空列表，迁移时须验证撤权不会先撤走仍有待还原窗口的屏。重新授权时优先处理恢复记录。伴侣应用的录屏权限用于截图；缺权时关闭截图并提供系统设置入口。RustDesk 的画面采集权限由 RustDesk 自行申请，两者需分别测试。

## 5. 身份、更新与排障

P0 同时修改应用 Bundle ID、显示名、签名配置、数据和日志路径、更新读取地址及发布目的地。正式名称和签名身份由项目确定。首次运行在独立目录创建配置，旧 Snug 的恢复记录留给原应用处理。检查菜单、欢迎页、启动参数、开机启动和诊断输出中的旧身份。README 与 LICENSE 保留项目来源和版权声明。

M2 的 `rd-check` 以只读方式报告系统与 RustDesk 版本（若可读取）、权限、信号来源与新鲜度、显示器数量及输入模式的验证状态；无样本、缺权限与确认为空闲使用不同结果。诊断只保留定位所需的事件类别、时序与错误原因，排除密码、密钥、原始输入内容和窗口标题。保留 [AppBundle](../Sources/Snug/Update/AppBundle.swift) 按当前应用签名要求验证候选包的逻辑，并测试原版包被拒绝。发版时验证签名、公证、升级后的应用身份与恢复数据兼容性；新更新源就绪前保持该通道关闭。

## 6. 实施顺序与放行证据

| 阶段 | 自动检查 | 必须取得的实际证据 |
|---|---|---|
| P0 解耦 | 运行 `scripts/snug check`（Swift 构建、Swift 测试、脚本单测）；检索 Sources、Tests、打包资源和脚本中的旧探针、进程名及发布目标，逐项核对。 | 原版和派生版并装，分别修改配置、授权、运行诊断，确认各自的路径、权限归属及更新目标。 |
| M0 单手机 | 用会话样本覆盖空闲、重复、过期、未知、重连及手动结束；沿用屏幕与手势测试，补来源过滤和释放按键后的状态。 | 记录两端版本、模式、显示排布和断开前后窗口及字号。逐项执行产品文档的 M0 表，单列手动兜底与未通过项。 |
| M1 多屏与恢复 | 用现有屏幕 fake 覆盖四档、外来显示器、恢复中断和重复恢复。 | 四档切入、跨屏移动、热拔屏、强杀重启、撤权再授权；核对其他显示器和窗口未被改动。 |
| M2 分发 | 校验包签名与更新目标，自检覆盖正常、空闲、未知、缺权。 | 在干净系统安装公证包，从自有通道升级；macOS 大版本变更后重跑建屏、输入和恢复场景。 |
| M3 可选 | 待 M0/M1 留下明确的手动选屏或机型配置障碍后另行设计。 | 独立记录客户端修改的收益、维护成本和许可证评估，再决定是否立项。 |

单元测试能证明状态转移与恢复策略，RustDesk 注入身份、客户端屏幕枚举和 macOS 权限行为都需要真机取证。当前设计尚未取得这三项结果。
